## Task 1 — System Mapping & Inspection

### 1.1 What this is

Focus Forest is a Manifest V3 Chromium extension ("gentle mission-aware browsing
companion"). The user plants an *intention* (a "mission"), browses, and the extension
grows a local "garden" — one node per page, parented by the link/tab/redirect that led
to it. At user-configurable depth thresholds the companion softens ("desaturated") and
then offers a *choice sheet* (keep exploring / return / save for later / new mission).
Nothing is blocked; everything stays in `chrome.storage.local`. Optional offline
"Forest Finds" (rewards) mark deliberate moments.

### 1.3 Data flow

```
page click / tab event
   │  (a) content script: LINK_CLICK / SPA_NAVIGATION / OBSERVE_PAGE / DISMISS_INTERVENTION
   │  (b) worker listeners: tabs.onUpdated → observeTab, webNavigation.onCommitted → nav hints,
   │      onHistoryStateUpdated → trackLink('spa'), onCreated/onUpdated → new-tab takeover
   ▼
service-worker onMessage (schema validated, rate-limited per sender) / direct listeners
   ▼
mutate() — single promise queue:
   loadState() [cached, invalidated by external chrome.storage.onChanged]
   → mutator mutates session graph in place (nodes[], events[], pendingRedirects[], activeIntervals[])
   → saveState() = normalizeState() + chrome.storage.local.set (retry once on transient write failure)
   → updateBadge()
   ▼
consumers:
   content chip  ← GET_ACTIVE_VIEW (compact view only; full snapshot denied to page contexts)
   popup/newtab  ← GET_SNAPSHOT, GO_HOME, START_MISSION, END_MISSION, COMPLETE_ONBOARDING
   dashboard     ← GET_SNAPSHOT, GET_DASHBOARD_STATS, PRUNE_NODE, DELETE_*, FORGET_SITE,
                   CLEAR_DATA, EXPORT/IMPORT_DATA, CHECK_STORAGE_QUOTA
   alarm (5 min) ← compactStateIfNeeded() when storage crosses quota thresholds
```

Key invariants maintained by `normalizeState` (the one gate every persisted read passes):
bounded arrays, http(s)/newtab-placeholder URLs only, safe enum states, legacy `tabId`
→ `tabIds`, legacy frozen-origin repair.

## Task 2 — Goal & Intent Reverse-Engineering

Reading the code — not just the README — the intended vision is unmistakable:

1. **A non-punitive attention instrument, not a blocker.** No request is ever intercepted
   or denied. The product's own copy codifies this: "Nothing is wrong — choose whether to
   keep exploring", rewards are explicitly "never points, never streaks", and a test suite
   asserts that reward copy contains no score/urgency words. The user's ultimate goal is
   *meta-awareness*: notice when a rabbit hole has become several branches deep, and make
   the return a deliberate choice.

2. **Structural truth about the browsing graph.** The engine goes to unusual lengths so
   the tree reflects *how* the user got where they are: pending-branch correlation for
   `target=_blank` links, multi-hop redirect resolution, opener-tab inference with
   confidence tiers (`direct` / `tab-inferred` / `external`), low-confidence marking for
   back/forward, dedupe of SPA history, and "forget" operations that repair surviving
   subtrees instead of deleting them. End goal: a tree the user can actually trust and
   retrace ("Pick a leaf to trace its path home").

3. **Local-first privacy as an architecture constraint.** Everything is
   `chrome.storage.local`; a test asserts settings are *never* mirrored to
   `storage.sync`; the content script is denied full snapshots (only a compact active
   view); `web_accessible_resources` is empty; the shadow DOM is closed; all dynamic DOM
   is built via `textContent`/DOM APIs (no innerHTML sink); extension CSP has no
   `unsafe-inline`; URLs are scheme-validated at every ingress (`safeHttpUrl`,
   `safeSessionUrl`). The README promise "Your curiosity belongs here… All data stays on
   this device" is enforced in code, and the user's goal includes resisting the
   extension becoming a tracking surface.

4. **Resilience under hostile and broken conditions.** Pages can outlive the extension
   (invalidated-context handling), storage can fail transiently (retry-once mutators),
   state can be poisoned (normalization + import validation), tabs can be reused after
   close (GO_HOME identity checks), and the worker can be suspended mid-queue
   (`onSuspend` flush). The user's goal is a companion that degrades silently, never
   loses the user's action, and never crashes the page it lives in.

5. **Cross-Chromium portability.** Brave/Edge/Opera/Vivaldi new-tab placeholders are
   recognized and taken over; `chrome.search` has a privacy-preserving fallback that is
   regression-tested to *never* silently pick Google.

In short: the user is building a **trustworthy, local-only, gentle browsing-reflection
tool whose tree is an accurate map of the user's own attention path** — and the audit
below is judged against that vision.

### S-1 — Stale toolbar badge after CLEAR_DATA

- **File & Line Area:** `background/service-worker.js`, `replaceState` (lines 153–163); triggered by `case 'CLEAR_DATA'` (line ~1101).
- **Failure Mode:** Every persisted *mutation* refreshes the badge via
  `runMutatorWithRetry → updateBadge()`, but `CLEAR_DATA`/`CLEAR_ALL_DATA` go through
  `replaceState()`, which bypasses that path entirely. With a mission in progress, the
  user clears local data from the dashboard; the session is gone from storage, but the
  toolbar keeps showing the live-mission badge (🌱 / depth color) until some unrelated
  mutation happens — in a cleared forest, it never will. Verified at runtime: with an
  active mission, `CLEAR_DATA` produced zero badge calls.
- **Original Code Fragment:**
```js
function replaceState(nextState) {
  const run = mutationQueue.then(async () => {
    await saveState(nextState);
    return nextState;
  });
  mutationQueue = run.catch((error) => {
    logError(error, { category: ERROR_CATEGORIES.STATE_MUTATION, component: 'service-worker', function: 'replaceState-catch' });
    clearStateCache();
    return undefined;
  });
  return run;
}
```
- **Fixed Code Replacement** (`background/service-worker.js`, now lines 153–167):
```js
function replaceState(nextState) {
  const run = mutationQueue.then(async () => {
    await saveState(nextState);
    // replaceState bypasses runMutatorWithRetry, so clear the toolbar badge
    // here: after CLEAR_DATA the mission is gone but the badge would otherwise
    // keep showing a live mission until an unrelated mutation happens.
    updateBadge();
    return nextState;
  });
  mutationQueue = run.catch((error) => {
    logError(error, { category: ERROR_CATEGORIES.STATE_MUTATION, component: 'service-worker', function: 'replaceState-catch' });
    clearStateCache();
    return undefined;
  });
  return run;
}
```
Verification: after `CLEAR_DATA` with an active mission, the worker now emits
`[['text',''],['color','#00000000']]`; existing badge tests (exactly-once set on start,
recolor at threshold, clear on end) still pass — `applyBadge` de-dupes no-ops.

### S-2 — Sessions-only import silently resets the user's rhythm

- **File & Line Area:** `background/service-worker.js`, `importAllData` (lines ~852–868, 929–940).
- **Failure Mode:** `importAllData` documents "replaces settings", but when the imported
  file contains *no* `settings` key at all, `normalizeState` produces
  `normalizeSettings(undefined)` = defaults. A sessions-only file (the most common
  partial import) therefore silently overwrote the user's tuned thresholds, excluded
  sites, search engine and rewards opt-in with factory defaults. Verified: settings
  `{gentleDepth:7, choiceDepth:9, enableRewards:true}` became
  `{gentleDepth:4, choiceDepth:5, …, enableRewards:false}` after importing a file that
  only contained `sessions`. This contradicts the end goal: importing history must not
  destroy preferences.
- **Original Code Fragment:**
```js
  const next = normalizeState({ ...incomingState, sessions: incomingSessions });
  return mutate((current) => {
    // ...
    Object.assign(current, {
      schemaVersion: SCHEMA_VERSION,
      sessions: mergedSessions,
      compostItems: Array.from(compostMap.values()).slice(0, LIMITS.COMPOST),
      rewardHistory: Array.from(rewardMap.values()).sort((a, b) => a.timestamp - b.timestamp),
      settings: next.settings,
      activeSessionId,
      onboardingCompleted: Boolean(current.onboardingCompleted || next.onboardingCompleted)
    });
```
- **Fixed Code Replacement** (`background/service-worker.js`, now lines 908–911 and 950–958):
```js
  // A sessions-only file must not be treated as "no settings": replacing the
  // user's tuned rhythm with defaults on every partial import silently resets
  // their thresholds. Only an explicit settings object overrides local ones.
  const incomingHasSettings = isRecord(incomingState.settings);
  const next = normalizeState({ ...incomingState, sessions: incomingSessions });
  return mutate((current) => {
    // ... (merge logic unchanged) ...
    Object.assign(current, {
      schemaVersion: SCHEMA_VERSION,
      sessions: mergedSessions,
      compostItems: Array.from(compostMap.values()).slice(0, LIMITS.COMPOST),
      rewardHistory: Array.from(rewardMap.values()).sort((a, b) => a.timestamp - b.timestamp),
      settings: incomingHasSettings ? next.settings : current.settings,
      activeSessionId,
      onboardingCompleted: Boolean(current.onboardingCompleted || next.onboardingCompleted)
    });
```
Verification: sessions-only import now preserves the local rhythm byte-for-byte, while
an explicit `settings` object in the payload still overrides (existing
"import applies the imported settings" test still passes).

### S-3 — Import can leave two "active" sessions (and resurrect completed ones)

- **File & Line Area:** `background/service-worker.js`, `importAllData` merge (lines ~915–925); `shared/state.js`, `normalizeState` active-pointer line (~470).
- **Failure Mode:** Two related inconsistencies in the imported-state surface:
  1. If the imported snapshot has its *own* active session (status `'active'`) and the
     local state has a *different* active session, the merge lets the import win the
     `activeSessionId` slot but leaves the local session `status:'active'` forever.
     Result: two "active" gardens; the chip/badge track the imported one; the user's
     real in-progress session is orphaned and can never complete. Verified: statuses

```js
    const mergedSessions = Array.from(sessionMap.values()).slice(-LIMITS.SESSIONS);
    const activeSessionId = mergedSessions.some((s) => s.id === next.activeSessionId)
      ? next.activeSessionId
      : (mergedSessions.some((s) => s.id === current.activeSessionId) ? current.activeSessionId : null);
    const compostMap = new Map();
```
- **Original Code Fragment (state.js):**
```js
  const activeSessionId = sessions.some((session) => session.id === value.activeSessionId) ? value.activeSessionId : null;
```
- **Fixed Code Replacement (worker)** (`background/service-worker.js`, now lines 925–940):
```js
    const mergedSessions = Array.from(sessionMap.values()).slice(-LIMITS.SESSIONS);
    const activeSessionId = mergedSessions.some((s) => s.id === next.activeSessionId)
      ? next.activeSessionId
      : (mergedSessions.some((s) => s.id === current.activeSessionId) ? current.activeSessionId : null);
    // When the import claims a *different* active garden, the displaced local

    // "active" forever while the chip tracks the imported one.
    if (activeSessionId && current.activeSessionId && activeSessionId !== current.activeSessionId) {
```

### S-4 — "Continue session" can never report a real return

- **File & Line Area:** `background/service-worker.js`, `GO_HOME` response (line 1132); `newtab/app.js`, resume handler (line 106).
- **Failure Mode:** `GO_HOME` responds with `{ ...activeView(...), reward }`, and
  `activeView` deliberately returns a *compact* session shape

  for page contexts). The New Tab resume button reads
  `view?.session?.origin?.url` — permanently `undefined` — so
  `hasRealDestination` was always `false` and the user always saw the fallback copy
  "Active intention ready — search or enter a URL to explore." even when GO_HOME had
  just focused/created the real origin tab. The success branch was dead code. Verified
  at runtime: `GO_HOME.session` keys were exactly `['id','mission','interventionPaused','node']`.
- **Original Code Fragment (worker):**
```js
        const { returned: didReturn, reward } = returnResult;
        if (!didReturn && hasRealOrigin) await chrome.tabs.create({ url: returnUrl, active: true });
        return { ...activeView(await loadState(), didReturn ? originTabId : null), reward };
```
- **Original Code Fragment (newtab):**
```js
    const view = await message('GO_HOME');
    status.hidden = false;
    const originUrl = view?.session?.origin?.url;
```
- **Fixed Code Replacement (worker)** (`background/service-worker.js`, now lines 1155–1161):
```js
        const { returned: didReturn, reward } = returnResult;
        if (!didReturn && hasRealOrigin) await chrome.tabs.create({ url: returnUrl, active: true });
        // Consumers (New Tab "Continue session") need the destination to report
        // a truthful outcome; activeView deliberately omits origin, so without
        // this field they could never tell a real return from a placeholder.
        return { ...activeView(await loadState(), didReturn ? originTabId : null), reward, origin: hasRealOrigin ? { url: returnUrl, tabId: originTabId } : null, returned: didReturn };
```

- **Fixed Code Replacement (newtab)** (`newtab/app.js`, now lines 104–111):
```js
  try {
    const view = await message('GO_HOME');
    status.hidden = false;
    // GO_HOME reports the destination in its own `origin` field; the compact
    // active view it embeds intentionally omits origin, so reading
    // view.session.origin.url was always undefined and this branch could

    const originUrl = view?.origin?.url;
```

`view.origin = null` → fallback copy (correct). The privacy boundary is intact: the
origin field is only present for http(s) URLs, and `GO_HOME` was already answerable by
content scripts (the chip uses it), so no new exposure surface is created.

### S-5 — Context-menu "Start Focus Mission" force-reloads the page (and ignores link targets)

```js
      const cleanUrl = safeHttpUrl(tab?.url);
      await createSession(mission, { id: tab?.id, url: cleanUrl || 'chrome://newtab', title: tab?.title || 'New Tab', windowId: tab?.windowId });
      if (tab?.id != null && cleanUrl) {
        await chrome.tabs.update(tab.id, { url: cleanUrl });
      }
    }
```
- **Fixed Code Replacement** (`background/service-worker.js`, now lines 986–1001):
```js
    if (info.menuItemId === 'focus-forest-start') {
```

### C-1 — Choice sheet lingers after the forest stops asking

- **File & Line Area:** `content/content.js`, `update()` (line 417).
- **Failure Mode:** The choice sheet is shown once per URL
  (`choiceCard.dataset.shownFor`), but nothing ever *hides* it when the view stops
  qualifying. `update()` only hid the card when the node disappeared or the site was
  paused. So the sequence "choice sheet appears at depth 5 → user follows a link back
  toward the root (or pauses the mission)" left the dialog pinned over the page —
  the forest no longer had anything to ask, yet the user was still confronted with
  "This path is deep, not wrong." at depth 2. This directly breaks the product's core
  gesture (a *gentle* offer that the user can walk away from).

### New findings (fixed)

**R2-1 (High — pre-existing, missed in pass 1): GO_HOME hard-reloads the origin page.**
`background/service-worker.js`, `GO_HOME` return branch. The guard
`sameOriginUrl(liveTab.url, origin.url)` already proves the tab is on the origin
page (canonical URLs match), yet the code then ran
`chrome.tabs.update(originTabId, { url: returnUrl, active: true })` — re-navigating
the tab to the page it already shows, i.e. a full reload that discards scroll,
form and SPA state on **every** "Return to my mission" / "Continue session" click
while the origin tab is alive. The same anti-pattern was fixed in the context menu
(S-5) but survived here. Notably, `test-service-worker.mjs` asserted the `url`
prop, i.e. the test pinned the bug.

V2: activate without navigating; the new-tab recovery path (tab gone / drifted)
is unchanged. The test now pins the no-reload contract:
`assert.equal(goHomeUpdate[2].url, undefined, …)`.

**R2-2 (Low — introduced by C-1): choice card hidden while holding focus strands focus.**
`content/content.js`, `update()`. When the card auto-hides (SPA navigation away
while the dismissal button held focus, pause, site pause), focus dropped to
`<body>`. V2: capture `shadow.activeElement` before hiding (the closed-shadow
view — `document.activeElement` only sees the host) and call the existing
`restorePageFocus()` when focus was inside the card. The same pre-existing flaw
in the `pause-site` branch (hiding the chip while its button held focus) was
fixed identically.

**R2-3 (Low — introduced by D-2): import rejection was silent.**
`dashboard/app.js` `importData()`. An oversized (or unparseable) file closed the
picker with zero user feedback. V2: a new `#import-status`
(`role="status" aria-live="polite"`, existing `.muted` class) reports oversized
files, parse/validation failures, and success.
